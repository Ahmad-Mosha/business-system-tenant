# Architecture

What exists today, and the conventions everything new is expected to follow.
This document describes the system as built. It is not a specification of the future -
see `docs/discovery/` for analysis and direction.

**Current state:** Slice 1b. Auth, authorization, catalog (imported live from
EasyOrders), order detail, assignment and status transitions all work end to end.
Order ingestion by webhook and the Bosta pull are not built yet.

**Known provider constraint:** EasyOrders has **no list-orders endpoint** - only
`GET /orders/:id`. Order ingestion is therefore webhook-only, and the reconciliation
sweep described in ADR-004 is impossible for that provider. A missed webhook cannot be
detected by polling; the mitigation still has to be chosen.

## Shape

A modular monolith. One deployable API, one web app, one database.

```
apps/web        Next.js (App Router). Renders; holds no business rules.
apps/api        NestJS. Owns every rule and every access decision.
packages/contracts   Zod schemas + types shared by both, so they cannot drift.
```

The browser only ever talks to the web origin. `/api/*` is rewritten to the API by
Next, which keeps the session cookie first-party and removes CORS from the picture.
Server components call the API directly, forwarding the caller's cookie.

## Modules (apps/api/src/modules)

| Module | Owns | Status |
|---|---|---|
| `identity` | users, roles, permissions, sessions, login | built |
| `audit` | append-only business history | built |
| `sales` | orders, lines, assignment, status transitions | built |
| `catalog` | products, variants, channel listings | built |
| `integrations/easyorders` | API client, catalog import | partial - webhook pending |

Modules for later slices do not exist yet. They are created when the slice that needs
them is built, not in anticipation.

## Conventions

| Concern | Rule |
|---|---|
| Ids | UUIDv7, generated by the application. Time-ordered, safe to expose. **Its prefix is a timestamp, so slicing the front of one is not unique.** |
| Money | `bigint` minor units (piastres) + explicit currency. Never floats. Converted to decimal only at the UI edge. |
| Time | `timestamptz`, stored UTC, rendered in Africa/Cairo. |
| Tenancy | `organization_id` on every business table, filtered in every query. One organization today. |
| Enums | Postgres enums, so an unexpected value cannot be written. |
| Errors | Every failure returns `{ error: { code, message, details? } }`. Domain failures carry a stable code. |
| Config | Validated by Zod at boot. A missing secret stops the process. |
| Unknown input | Never defaulted or guessed. Rejected, or raised for a human. |

## Security posture

- Sessions are opaque server-side tokens; only the SHA-256 is stored, so a database
  leak cannot be replayed as a live session.
- Passwords are argon2id. Login verifies against a decoy hash when the email does not
  exist, so response timing does not reveal which addresses are real.
- Every route is private unless explicitly marked `@Public`. Forgetting a decorator
  locks a route down rather than exposing it.
- Changing a password revokes every other session for that user.
- Rate limiting applies to the credential routes only, keyed on **IP and email
  together** - see ADR-003 for why the obvious alternatives are worse.

## Types and DTOs

There are no hand-written `*.dto.ts` classes with `class-validator` decorators.
Instead, every request and response shape is a **Zod schema** in
`packages/contracts`, and the TypeScript type is derived from that same schema
with `z.infer<...>` - so the compile-time type and the runtime validator can
never drift apart, which is a real failure mode of the class-DTO pattern (the
decorator says one thing, the type says another, and nothing catches it).

`ZodValidationPipe` enforces the schema at the controller boundary; every
controller method's parameter and return types come from `@app/contracts`, so
the same type is shared by the API and the Next.js app with no duplication.
`@typescript-eslint/no-explicit-any` is `error`, not `warn` - the build fails
if one appears. The database layer is Drizzle's typed schema builder, not
raw SQL strings, so a column rename is a type error everywhere it's read.

If Swagger/OpenAPI generation becomes a real requirement (e.g. an external
integrator needs a spec to code against), Zod schemas convert to OpenAPI
directly - this doesn't require moving to class-based DTOs.

## Testing

- Unit tests for rules that stand alone (scope resolution).
- End-to-end tests through the HTTP API against a real Postgres. No mocked database.
- Authorization is asserted **against API responses**, never through the UI: the API is
  the boundary an attacker reaches.

## Decided, not yet built

Settled during discovery so they are not relitigated when the slice arrives:

- **Stock and money will be append-only ledgers** with balances derived by summing, and
  projections for speed. Not general event sourcing - only these two need to be
  provably reconstructible.
- **Marketplace ingestion maps every source onto a small set of typed business
  documents**, so the domain never learns whether data arrived by API, webhook or file.
- **Costs are snapshotted onto outbound stock movements**, making historical COGS
  immutable.
- **`DELIVERED` / `RETURNED` belong to the courier**, and are deliberately absent from
  the order lifecycle until that integration exists.
