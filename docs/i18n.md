# Arabic and English — how the frontend speaks both

Prime Market's web app runs in Arabic (the default for first-time visitors) and
English. Every screen is on this — a new screen follows the same rules, and
lint refuses one that doesn't.

## Where the language comes from

- **A cookie, `NEXT_LOCALE`** (`ar` / `en`), set by the language switcher — in
  the user menu, and on the sign-in screen. This browser only; there is no
  account setting, by decision (2026-09-14).
- `src/i18n/config.ts` holds the languages and what follows from each;
  `src/i18n/request.ts` reads the cookie for every request (next-intl, no
  locale in the URL — every route and link stays as it is).
- The root layout sets `<html lang dir>` and wraps the app in next-intl's
  provider and Radix's `DirectionProvider`. Nothing else checks the language to
  lay itself out.

## Words: `src/messages/{en,ar}.json`

- English is the source of truth. Keys are type-checked (`src/i18n/types.d.ts`)
  and `src/i18n/messages.test.ts` fails if Arabic misses a key, a placeholder
  or a tag.
- Server components: `const t = await getTranslations('ns')`. Client and plain
  components: `const t = useTranslations('ns')`. Server actions use
  `getTranslations` too.
- **One namespace per module** — `orders`, `shipments`, `inventory`,
  `product`, `money`, `noon`, `team` — plus shared ones: `common`, `nouns`,
  `enums`, `validation`, `errors`, `table`, `filters`, `nav`.
- **Counts are ICU plurals**, and a counted noun lives in `nouns.*` (orders,
  products, items, units, invoices…). Arabic has six forms — never `${n} items`:
  `"{count, plural, =0 {لا توجد طلبات} one {طلب واحد} two {طلبان} few {# طلبات} many {# طلبًا} other {# طلب}}"`.
- **Statuses and types live in `enums.*`**, keyed by the API's value
  (`enums.orderStatus.DELIVERED`). Code keeps only the codes and how they look
  (tones, icons, order): `CATEGORIES`, `VOUCHER_COUNTERS`, `CASH_IN` /
  `CASH_OUT`, `PAID_TONE`, `stockState()`. A value the API may add later is
  checked with `isOneOf(list, value)` (`lib/utils.ts`) and shows as-is when
  unknown — never a guessed name.
- **Form checks** say what's wrong from `validation.*`; the order of checks
  stays in the action.
- **Sentences with data in them** use `t.rich` and the shared tags in
  `src/i18n/rich.tsx`: `<bdi>` for a name, date or search term, `<num>` for a
  figure, `<b>` for the figure a sentence is about, `<strong>` for a name it's
  about. Never build a sentence from pieces — word order differs.
- **Not translated — business data:** product and customer names, SKUs, noon
  partner / Amazon seller SKUs, order and tracking numbers, supplier names,
  notes people type, governorates (Bosta's Arabic names), file names.
  Bilingual reference data the API sends (ledger accounts' `nameAr` /
  `nameEn`) is picked by language with `accountName(account, locale)`.
- Lint (`eslint.config.mjs`) fails on text in JSX, in a text prop (`label`,
  `placeholder`, `title`, `aria-label`…), in a toast, or in an action's
  `message`. A message key (`'codHint'`) is not text; a capitalised word or a
  phrase is.

## The API's words: `lib/api-request.ts`

Every server action calls the API through `apiRequest()`, which answers
`{ ok: true, data }` or `{ ok: false, message }`. When the API gives a reason,
that's the message; when it doesn't (down, or a bare status), the message is
ours, from `errors.*`, in the reader's language. **This is the one place API
errors become words** — the planned API error codes get translated here, and
no screen changes.

Still in English until then, because the API writes them: its error reasons,
and the memo it writes on some ledger entries ("Payment to …", "Purchase
invoice"). Bosta's own text shows only for a state our API doesn't name.

## Direction

- `components.json` has `"rtl": true`: shadcn components are added — and were
  migrated (`shadcn migrate rtl`) — with logical classes. Write `ms- me- ps- pe-
  start- end- text-start text-end border-s border-e`, never `ml- pr- left- text-right`.
- **Icons:** arrows and chevrons that mean *forward/back* flip —
  `rtl:rotate-180` for horizontal ones, `rtl:-scale-x-100` for diagonals (a
  rotation would turn ↗ into ↙). Trend arrows (up/down) don't.
- **Sheets** take `side="start" | "end"` (default `end`, the reading end). The
  sidebar's sides are logical too: it sits on the right in Arabic.
- **Mixed text:** `<bdi>` around data inside a sentence. `Amount` isolates money
  left-to-right so a minus never jumps sides; any other figure with a sign
  written by hand (`+100`, `+12.5%`), and every phone number (`+20…`), goes in
  a `<bdi>` for the same reason. An Arabic range reads "1 إلى 20", not "1–20"
  (the dash reverses in RTL) — dates use `common.dateRange`.
- **Fields:** a `dir="auto"` field (names, notes) takes its direction from what
  is typed; empty, it follows the page, so an Arabic placeholder sits at the
  right edge (`globals.css`).

## Numbers, dates, money

- Locales `ar-EG-u-nu-latn` and `en-GB`: Egyptian Arabic month names and ج.م,
  **Western digits in both** (decision 2026-09-14), day-first English.
- Every date/time is in **Cairo time** (`Africa/Cairo`), whatever zone the
  server runs in. Things recorded from a date alone print without a time.
- `getFormat()` (async server) / `useFormat()` (everything else) —
  `src/i18n/format.ts`: `date`, `dateTime`, `time`, `day` ("Today" / "اليوم"),
  `month`, `count`, `compact` ("1.3 مليون"), `byDay`. Percentages go through
  ICU: `{share, number, percent}`.
- Money reads identically in both languages (`1,234,567.50`), so `money()` and
  `Amount` stay in `lib/`; the currency label is `common.egp` (EGP · ج.م).

## Charts

Geometry is always laid out left to right (Recharts assumes it); each chart
mirrors by kind, not blanket: **time series keep time left→right** — the most
common pattern in Arabic charts (IEEE VIS 2024) and the way digits read;
**breakdowns mirror** — label at the reading start, bar growing leftward.
Ticks, tooltips and legends are in the reader's language; tooltips read RTL,
and an Arabic tick ("17 أغسطس", "850 ألف") is isolated right-to-left inside
the left-to-right SVG, so its number sits on the correct side.
